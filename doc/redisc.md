# English Version

## 1. Introduction

NAND flash-based storage has been widely adopted in servers, mobile devices, and embedded systems due to its high random-access performance, low power consumption, and compact form factor. Unlike magnetic disks, flash memory cannot overwrite data in place. Data can be programmed at page granularity, while erase operations are performed at a larger block granularity. To expose a conventional block-device interface, flash devices rely on a Flash Translation Layer (FTL) to maintain logical-to-physical mappings and perform garbage collection (GC). During GC, valid pages in victim blocks must be migrated before the blocks can be erased. If the device cannot distinguish file-system-invalid data from truly valid data, it may unnecessarily copy pages that have already been invalidated by the file system, increasing write amplification and degrading both performance and lifetime.

Discard/TRIM is introduced to bridge this host-device semantic gap. By issuing discard commands, the file system informs the block device that certain logical address ranges no longer contain valid data. The device can then avoid migrating these invalidated pages during future GC. Therefore, discard is important for reducing write amplification and improving long-term reclaim efficiency. However, discard is not free. A discard command still traverses the host I/O stack, the block-layer queue, and device-side metadata processing paths, and may compete with foreground reads and writes. Prior work has shown a clear trade-off between the benefit and overhead of TRIM/discard: issuing discard too late increases unnecessary GC copying, while issuing discard too aggressively may introduce I/O contention and command processing overhead.

F2FS is a log-structured file system designed for flash storage. With out-of-place update, F2FS writes updated data to new locations and marks the old blocks invalid. This design improves write sequentiality but continuously creates invalid blocks that must eventually be reclaimed. F2FS already provides flexible discard controls, such as discard granularity, I/O-aware discard, the maximum number of discard requests per round, and background issue intervals. These controls allow F2FS to regulate discard issuance according to the current I/O state and pending discard queue state, preventing uncontrolled discard from interfering with foreground requests.

However, discard command formation in F2FS is not an instantaneous action. Invalid blocks first go through segment metadata, dirty segments, prefree segments, checkpoint-related paths, and pending discard structures before they are submitted to the device by the discard issue thread. In other words, the issue thread observes already-formed pending commands, whose length, count, and spatial shape have already been influenced by upstream update, GC, and checkpoint paths. Existing discard controls mainly decide how already-formed commands should be issued, but they do not explicitly model the short-term evolution and spatial structure of these commands before and during their formation.

The key observation of this paper is that many small discards in F2FS should not be treated as isolated small requests. Some of them are early fragments of a local segment-window that continues to mature rapidly; issuing them too early may lose the opportunity to merge with nearby follow-up commands. Meanwhile, issue-side waiting alone cannot eliminate all small discards, because part of discard fragmentation has already been formed before commands enter the pending queue. When discardable blocks in a segment are separated by a small number of live blocks, the discardable space may be large in total, but it can only appear as multiple non-contiguous discard ranges. The issue thread cannot safely merge such ranges across live blocks without violating correctness.

Based on this observation, we propose **ReDisc**, a segment-window-aware discard handling mechanism for F2FS. ReDisc does not replace the existing checkpoint, prefree, discard materialization, or issue paths. Instead, it adds window-level opportunity detection and demand shaping on top of the existing F2FS discard framework. ReDisc consists of three coordinated modules. First, **SWOD** identifies promising segment-windows in the pending discard queue and holds their commands for a bounded time to capture short-term follow-ups. Second, **WCE** prioritizes cleaning around held windows to reduce residual live blocks, allowing these windows to naturally evolve into more continuous discard ranges. Third, **SFI** conservatively suppresses new tiny fragments in non-target regions, reducing the formation of future small discard commands.

ReDisc follows a conservative correctness principle: it never issues discard across live blocks, never fabricates a continuous discard range, and never changes the semantic range of existing F2FS discard commands. Which blocks can be discarded, how discard ranges are materialized, and when commands are submitted to the device are still determined by the original F2FS paths. ReDisc shifts the observation granularity from individual commands to segment-windows, enabling the system to preserve short-term issue-side merge opportunities while reducing upstream formation of future discard fragmentation.

This paper makes the following contributions:

* We point out that F2FS discard handling should not be understood solely from the current length of an individual pending command; the short-term evolution of local segment-windows and the distribution of live blocks also determine the final shape of discard commands.
* We identify two sources of small discard: some small commands have short-term follow-up opportunities that can be captured by bounded issue-side waiting, while others are caused by live-block holes before commands enter the pending queue.
* We design and implement ReDisc, which combines SWOD, WCE, and SFI to preserve short-term merge opportunities and reduce future tiny fragments without changing the correctness semantics of F2FS discard.
* We evaluate ReDisc under real workloads and show that segment-window-aware discard handling can reduce premature issuance and improve the regularity of discard ranges.

## 2. Background

### 2.1 Flash Storage, Garbage Collection, and Discard

NAND flash memory cannot be overwritten in place like magnetic disks. Data is programmed at page granularity, while erase operations are performed at block granularity. To provide a conventional block interface to the host, flash devices use an FTL to maintain mappings from logical block addresses to physical flash pages. When the host updates a logical address, the device usually writes the new version to another physical location and marks the old physical page invalid. As writes continue, invalid pages accumulate, and the device must perform device-level garbage collection to reclaim free blocks.

During device-level GC, the device selects victim blocks, migrates still-valid pages to other locations, and then erases the victim blocks. If some data has already been invalidated at the file-system level but the device is not aware of this invalidation, the device will still migrate such pages as valid data. These unnecessary migrations increase write amplification and may add latency to foreground writes when GC lies on the critical path.

Discard, also known as TRIM, is the interface through which the file system communicates invalidation information to the device. A discard command tells the device that a logical block range no longer contains valid data. After receiving this information, the device can update its internal mapping or validity state so that future GC no longer migrates these pages. As a result, discard can reduce write amplification and improve reclaim efficiency.

At the same time, discard introduces overhead. On the host side, discard commands pass through the file system, the block layer, and I/O queues, where they may compete with normal reads and writes. On the device side, discard may involve mapping-cache lookup, mapping-table update, buffer invalidation, and metadata writeback. The overhead depends on command size, address continuity, mapping-cache state, and device implementation. Therefore, discard handling must balance two effects: issuing discard too late increases unnecessary GC copying, while issuing discard too early or too aggressively increases immediate I/O contention and command-processing overhead.

### 2.2 F2FS Space Management and Update Behavior

F2FS is a log-structured file system designed for flash-based storage. It divides the main area into segments, and a segment is an important management unit in F2FS, typically consisting of 512 blocks. F2FS adopts out-of-place update: when file data is updated, the new version is written to a new free location, while the old blocks are marked invalid. This converts random updates into a more sequential write pattern, but it continuously produces invalid blocks.

F2FS maintains several metadata structures to track space status. The Segment Information Table (SIT) records the number of valid blocks and the validity bitmap for each segment. Dirty segment lists track segments containing invalid blocks. Checkpointing persists key metadata and provides a consistent recovery point. Garbage collection reclaims file-system-level free space. Foreground GC is triggered when free space is insufficient for incoming writes, while background GC prepares reclaimable space in the background to reduce future foreground pressure.

Because both out-of-place update and GC change block validity, invalid blocks in F2FS are the source of future discard demand. However, invalid blocks do not immediately become device-visible discard commands. They must first be reflected in segment metadata, dirty/prefree states, and checkpoint-related paths before they can be materialized as pending discard commands. Therefore, understanding F2FS discard behavior requires considering invalid-block formation, pending-command generation, and final issuance by the discard thread.

### 2.3 F2FS Discard Lifecycle and Control

F2FS discard handling can be viewed as a multi-stage lifecycle. First, file updates, deletions, and GC invalidate old blocks. Second, these invalidation events are organized and persisted through SIT, dirty segments, prefree segments, and checkpoint-related paths. Third, F2FS converts discardable logical address ranges into pending discard commands and inserts them into internal discard management structures. Finally, the discard issue thread selects commands from the pending queue and submits them to the block layer and the device.

F2FS already provides several discard control interfaces. `discard_granularity` controls whether very small discard ranges should be issued. `discard_io_aware` allows the discard thread to yield when foreground I/O is active. `max_discard_request` limits the number of discard commands submitted in one round. Issue intervals control the rhythm of background discard. Together, these mechanisms provide downstream control over discard consumption and help avoid uncontrolled interference with foreground I/O.

The common characteristic of these mechanisms is that they mainly act after pending commands have already been formed. They can observe the current command length, pending-queue pressure, and foreground I/O status, but they do not directly characterize whether a local segment-window is still rapidly maturing, nor do they change the spatial shape of future discard demand before it enters the pending queue. This distinction is central to the problem studied in this paper: a small pending discard command may be an isolated fragment, or it may be an early fragment of a local window; a highly discardable segment-window may still be split into many non-contiguous discard ranges by a small number of live blocks. The former calls for issue-side recognition of short-term merge opportunities, while the latter requires understanding the spatial origin of discard fragmentation before pending commands are formed.
